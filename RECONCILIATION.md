# Chatwoot message reconciliation (Chatwoot 4.20.1)

The bridge stores accepted webhooks in SQLite. A webhook that could not reach the bridge is not retried by Chatwoot 4.20.1. When `RECONCILIATION_INBOX_ID` is set, every 30 seconds the bridge also checks that inbox through the Chatwoot API, and enqueues missing public incoming messages using the same `message:<account>:<id>` key as the webhook. Outgoing messages and private notes are never replayed by this scan. Without this environment variable reconciliation is disabled; accepted webhooks still use the queue.

## First activation on an existing deployment

Set `RECONCILIATION_INBOX_ID` to the single inbox that the service user can access. Enable signed webhooks with `CHATWOOT_WEBHOOK_SECRET`, and set `CHATWOOT_BRIDGE_USER_ID` to the numeric ID of a dedicated bridge-only Chatwoot user whose API token is configured. Startup verifies the token's profile ID and refuses a mismatch. For a safely authenticated outgoing echo, the bridge requires the signed event and a matching random marker in `content_attributes` previously saved for this exact account, conversation, and service user. This marker does not set `source_id`, which would suppress sending to some channels. Without these settings reconciliation does not start; legacy mode without them does not provide this echo protection. Before stopping the old bridge, capture the current UNIX timestamp in seconds and set `RECONCILIATION_BASELINE_UNIX` to it. The timestamp may be moved earlier only to a time after the durable queue was installed and confirmed active: older deliveries may not have queue keys and could be duplicated. Keep the old database when upgrading. Existing message mappings are used to skip already forwarded IDs, but legacy mappings do not prove that every attachment was delivered. The first enabled startup saves this boundary in SQLite; subsequent restarts use the saved value even if the environment variable changes. Without a valid initial boundary enabled reconciliation fails startup rather than guess. Messages lost before that boundary require separately verified, targeted recovery.

The scan persists its checkpoint only after the full pass, including both inbox-access checks. If an API request fails, the checkpoint stays unchanged, `/health` returns 503, and the next pass retries. A failed earlier scan may have inserted some events; unique durable queue keys suppress repeated insertions. Sent payloads are removed from the queue after delivery; event keys remain. Pending and recovered messages can arrive out of order when live webhooks race a recovery scan.

The checkpoint is bound to its account and inbox; changing either fails startup rather than reusing a different source's watermark. A pre-existing checkpoint without this source identity also fails closed. Plan source changes as a separate migration and choose a new baseline deliberately. The schema version in this upstream candidate is independent of other forks' migration numbers; matching version numbers do not imply compatible databases. Never use it against a fork's live database without separately checking and migrating its schema.

Pending queue payloads contain message and contact data and can include signed attachment URLs. Protect the SQLite database, its WAL/SHM files, backups and filesystem access accordingly. Clearing a delivered row's payload does not securely erase bytes from old SQLite pages, WAL or backups. Delivered deduplication keys are retained indefinitely, so storage grows; choose and validate a retention strategy before long-term use. Removing keys too early permits old duplicates to be replayed.

## Bounds and operational limits

* This relies on the bridge service user retaining access to **all conversations** in the selected inbox. A successful inbox access check does not establish that the conversation API exposes all conversations: Chatwoot also applies user permissions. Confirm the service user's permissions independently. For `updated_within`, Chatwoot 4.20.1 returns all matching conversations without pagination. The bridge caps this response at 20 MiB; exceeding that cap stops checkpoint advancement and degrades health, requiring operator intervention.
* Chatwoot messages use ID interval filtering with an upper limit of 1000. On a full or oversized response the bridge recursively divides the ID interval, avoiding ID/timestamp order assumptions. Each response is capped at 20 MiB. If one message alone exceeds that cap, or there are more than 10,000 interval requests in one conversation, the scan fails closed. All message history of each changed conversation is read, though only the recent overlap is eligible for recovery. This adds API load as history grows.
* The initial boundary excludes earlier missing messages. Each later scan accepts messages with `created_at` no earlier than the last completed checkpoint minus 120 seconds, bounded by the initial boundary. Clock skew, backdated messages, delayed commits or visibility exceeding that overlap can lead to gaps. Deleting messages/conversations before the scan or losing the SQLite volume also prevents normal recovery. Changing the clock backwards stops advancement when detected; operators should monitor `/health` and keep the system clock synchronized.
* The 120-second overlap is not a proof of exactly-once or loss-free delivery under arbitrary failures. Existing outgoing-message loop suppression has separate limitations. This mechanism is not a replacement for backups or monitoring.
* A stalled worker is reported unhealthy after five minutes without starting a second parallel worker. A send/topic-creation intent is committed before calling Telegram; mapping, progress and clearing that intent are committed together afterward. If a response is ambiguous or the process stops during the call, the event remains blocked for operator review instead of being resent. Other conversations continue. This can produce a false alarm when the crash precedes transmission, so inspect the actual topic before resolving it. Exactly-once delivery across external services remains impossible without provider idempotency.
* If a Telegram topic is deleted after part of a message was confirmed, the event stays pending for manual recovery. The bridge will not automatically put only the remaining attachments in a replacement topic, where the original text would be missing.
* This only scans incoming messages. Webhook status updates are not reconciled. Chatwoot message creation is attempted once: any error after the POST starts, including an HTTP 4xx, is ambiguous. The update identifier and source marker are retained as pending until an operator checks Chatwoot; the original text and files are not retained by this registry and are never retried blindly. If a verified absent reply needs resending, send a new Telegram message.
* Telegram URL fallback is attempted only for a positively identified URL rejection, not for timeouts, invalid responses, or 5xx. Oversized attachments may still be represented by a link. A message mapping alone does not prove every attachment was delivered.

## Attachment download origins

The configured `CHATWOOT_BASE_URL` is trusted only for `/rails/active_storage/`; its API token is never sent to external origins. HTTP on that configured origin remains supported but transmits data and credentials without encryption. For fallback downloads from an external or internal object store, explicitly set `ATTACHMENT_DOWNLOAD_ORIGINS` to a comma-separated list of exact HTTPS origins, for example `https://storage.example.test,https://cdn.example.test:8443`. No wildcards, credentials, paths, queries or HTTP object-storage origins are allowed. Every redirect is checked before the next request, and external requests receive no Chatwoot token. The list trusts the configured origins and their DNS. S3 deployments that previously relied on unrestricted redirects must explicitly configure their origin; otherwise the attachment stays pending, the health check degrades and the error identifies the missing origin configuration. No URL or query should be logged.

## Resolving an unknown outcome

Never retry an uncertain operation until checking the actual Telegram topic or Chatwoot conversation. Stop **all** bridge instances first, make a protected backup of the database and WAL/SHM, and build the application (`npm run build`). An OS-backed SQLite sidecar lock prevents a second bridge or the recovery CLI from running while the first owns the database. The small `*.bridge-lock` file is a lock artifact, not the queue; do not delete it to defeat a running lock. The same shared database must be used by only one active process; separate databases cannot deduplicate each other.

Run `node scripts/resolve-recovery.cjs /path/to/mappings.db list` locally. It lists record IDs and operation types, not message text. The database and the command output remain sensitive. For `queue` rows, after positively checking Telegram:

The production image includes this script and its compiled lock module. After stopping the bridge, a deployment using a named Docker volume can run it offline, for example `docker run --rm --network none -v BRIDGE_DATA:/app/data IMAGE node /app/scripts/resolve-recovery.cjs /app/data/mappings.db list`, replacing `BRIDGE_DATA`, `IMAGE` and the database path with the actual deployment values. Use the same mounted directory and file as the bridge; no bot or API secrets are required. Apply the same `queue`/`outgoing` actions below by replacing `list` in that command. Do not mount a separate copy when you intend to resolve the real queue.

* If the indicated operation **did not happen**, run `node scripts/resolve-recovery.cjs /path/to/mappings.db queue <id> retry`.
* If a text chunk or attachment **did happen**, obtain the exact Telegram message ID and run `node scripts/resolve-recovery.cjs /path/to/mappings.db queue <id> delivered <message-id>`. Mapping and progress are committed together.
* If `inflight` is `topic` and the topic **was created**, verify the exact topic ID from the Telegram topic link or a trusted administrator and run `node scripts/resolve-recovery.cjs /path/to/mappings.db queue <id> delivered <topic-id>`. Do not guess an ID or use the ID of a message within the topic. If it cannot be verified, leave the record blocked and investigate.

For an `outgoing` row, inspect the Chatwoot conversation first. Use `node scripts/resolve-recovery.cjs /path/to/mappings.db outgoing <id> delivered` only when the reply exists, or `... outgoing <id> not-delivered` only when absence is confirmed. The latter does not replay the original Telegram update: send a new Telegram message after inspection. Resume the bridge and verify `/health` and the conversation. These commands do not create an unauthenticated network endpoint.
